# フロントからバックエンドへの実装依頼

2026-09-20 時点。フロントで用意している操作を、サーバー保存・プラン生成につなげたいです。
ニックネーム／プロフィール機能は不要になったため、バックエンド対応も不要です。
ホーム右上はノートのアイコンから「次のデートに活かすこと」をモーダル表示する形に変更しました。

以下の項目は実装依頼です。API パス・DTO はまだ確定していません。`src/contracts` で入出力・エラー・状態を定義し、両担当で確認後、フロント側で hooks と画面を接続します。

## 1. カレンダーの予定一覧（優先）

- 現在：予定の作成・確定は保存されますが、一覧取得 API がなく、ホームは fixture のみ予定表示できます。
- 依頼：ログインユーザーの予定一覧を月・日付範囲で取得できるようにしてください。
- 表示に必要な情報：セッション ID、日付、開始・終了時刻、状態、表示タイトル。
- 完了条件：確定した予定が、ホームへの復帰・再読込後も表示され、対象プランを開けること。下書きの表示方針も契約で明確にしてください。
- フロント：`src/client/hooks/use-calendar-plans.ts`

## 2. 振り返りのスタンプ・タイトル・メモ（優先）

- 現在：`localStorage` に日付単位で保存しています。サーバーの振り返りやセッション状態には反映されません。
- 依頼：作成・取得・更新と、カレンダー表示用の取得を実装してください。
- 現在の入力：`date`、`title`（60文字以内）、`note`（500文字以内）、`mood`。
- スタンプ：`happy`（うれしそう）、`relaxed`（くつろいでいた）、`tired`（疲れていそう）、`sad`（戸惑い・退屈そう）。相手の様子についてのユーザーの観察です。
- 要調整：現 UI は1日1記録です。同日に複数予定がある場合の扱いと、セッションへの紐付けを決めたいです。
- 記録の保存と、AI が今後使う記憶への採用は区別してください。記憶候補にする場合は、観察を相手の発言・確定した好みとして扱わず、必要な確認・承認を経由させたいです。
- 既存 `REFLECTION` は固定質問で、今回の自由記述を受け取る経路がありません。入力の受け渡しと、保存後の状態遷移も対応をお願いします。
- 完了条件：再読込・別端末でも記録を取得・編集できること。保存結果がカレンダーに反映されること。
- フロント：`src/client/hooks/use-date-journal.ts`、`src/features/home/home-screen.tsx`

## 3. 「次のデートに活かすこと」のメモ（優先）

- 現在：新規追加は `localStorage` のみです。サーバーの記憶一覧と並べて表示していますが、新規メモはプランナーに渡りません。
- 依頼：メモの新規保存・一覧取得・編集・削除または無効化と、プラン生成への反映を実装してください。新規入力は現 UI で300文字以内です。
- 要調整：ユーザーが直接追加したメモの採用タイミング、次回だけ／継続利用の範囲、初回プラン作成前に保存するための所有者・couple の扱い。
- 既存の記憶編集は承認候補を作りますが、フロントに承認一覧がなく、レスポンスの `approvalId` も未使用です。候補・承認状態を取得できる契約が必要です。
- バックエンドの `reviseMemory` は承認の `sessionId` に `reflectionId` を設定しています。編集対象の記憶 ID と承認を明示的に結びつけ、承認時に対象の記憶だけ更新するよう確認をお願いします。
- 完了条件：追加したメモがサーバーに残り、利用可能になったメモが次のプランに渡ること。編集が承認待ちのまま操作不能にならないこと。
- フロント：`src/features/memory/memory-screen.tsx`、`src/client/hooks/use-memory.ts`

## 4. ホームの「AIからの提案」

- 現在：固定文言です。クリックすると固定の希望文をプラン作成フォームへ渡します。
- 依頼：利用可能な記憶・履歴を踏まえた提案を取得できるようにしてください。履歴がない場合の提案も必要です。
- 表示に必要な情報：提案 ID、見出し、短い説明、プラン作成に渡す希望文。生成中・取得失敗・提案なしの扱いも契約化してください。
- 完了条件：返された提案を表示し、その内容を引き継いでプラン作成できること。生成頻度・キャッシュはバックエンド側で設計をお願いします。
- フロント：`src/features/home/home-screen.tsx` の `ideas` と提案カード。

## 5. 「ここを変えたい」・プラン全体への変更希望

- 現在：入力 UI はありますが、fixture 以外は送信無効です。
- 既存：`REPLAN` API はあります。ただし希望文を `trigger` に保存しても、現在の生成処理では参照していません。
- 依頼：希望文（現 UI は1000文字以内）、対象行程 ID（全体の場合は省略）、元のプランバージョンを明確に受け取り、候補検索・再計画へ反映してください。表示名や自然文から対象 ID を抽出する方式は避けたいです。
- 固定予定・訪問済みの予定を維持し、変更できない場合の理由も返してください。変更案・差分・承認要否を現在の実行状態と接続してください。
- 完了条件：希望が変更案に反映され、承認後に行程が更新されること。反映不能・失敗・競合を画面で説明できること。
- フロント：`src/features/session/session-screen.tsx`

## 6. 集合・解散場所

- 現在：自由入力の場所名に対して、送信座標はデモ設定値、スポット ID は `mock:nagoya-station` 固定です。
- 依頼：場所の検索・候補選択に必要な API と、名前・座標・スポット ID が一致する地点情報を返してください。集合と解散は別々に指定します。
- プランの検索エリア・移動時間計算にも、選択した実際の地点を反映してください。曖昧な場所や検索失敗を既定座標へ黙って置き換えないでください。
- 完了条件：名古屋駅以外を選んだ場合も、その地点で候補検索・経路計算できること。
- フロント：`src/features/home/plan-form.tsx`

## 関連する候補検索の対応

作成 UI は食事・カフェ・海・温泉・水族館・映画などの希望を受け付けますが、現在の検索カテゴリは「散歩・展示・甘いもの」に固定されています。希望に応じて候補検索を変えられるようにしてください。対応外の場合は、その旨を画面へ返せるようにしたいです。

## 役割分担と受け渡し

- バックエンド：認証・所有権確認、保存、一覧取得、計画生成への反映、実行状態・エラーの定義。
- フロント：API クライアントと hooks、読み込み・失敗・空状態、承認 UI、保存後の画面更新。
- 共有：`src/contracts` の DTO と意味、記録と記憶の区別、日付／セッション単位、承認・利用範囲。両担当でレビューします。
- 既存のブラウザ保存データは、移行の有無と方法を合意するまでは削除しません。
- fixture での成功だけでなく、実 API で保存→再取得→画面表示→計画への反映まで確認して完了としたいです。
