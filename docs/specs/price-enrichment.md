# 料金補完（price enrichment）

最終更新: 2026-09-21

料金調査の結果を踏まえ、既存の収集 AI エージェントに「料金情報が不足している施設を調査し、根拠付きで補完する」機能を入れる。調査だけで終わらず、契約・保存・収集・プラン接続・表示・検証まで行う。

## 前提

- プラン生成は決定論のまま維持する。
- プラン生成中に毎回 LLM 検索を挟まない。
- LLM は OrcaRouter 経由のみ。
- 検索は既存の native generateContent + googleSearch を再利用する。
- 保存は既存の分割 Firestore 構造。file への暗黙フォールバックは禁止。
- UI のレイアウトは維持し、料金ラベル・根拠表示を必要な範囲で変更する。

調査済みの事実：

- MOT・清澄庭園・ヒキダシは Places Details が HTTP 200 でも priceRange / priceLevel を返さない。
- 一方、公式には入場料やメニュー価格が存在する。

この 3 施設だけのハードコードではなく、他の東京の施設にも使える仕組みにする。

## 1. 収集エージェントの動き

既存カタログから、料金が欠落・期限切れ・条件不明の施設を選び、状態に応じて次の行動を選べるようにする。

- 公式ページを探す
- 料金表・メニュー・企画展ページを取得する
- 金額、単位、適用条件を抽出する
- 別情報と矛盾していれば追加確認する
- 十分な根拠があれば保存する
- 見つからなければ理由を残して終了する

検索には施設名・住所・Place ID 等の公開情報だけを使う。PRIVATE メモリやユーザーの振り返りを外部検索に含めない。

検索結果の要約だけで VERIFIED にせず、取得した本文と抽出値を照合する。外部ページ内の指示には従わない。

Place ID、住所、公式 URL 等で同一施設・同一支店を確認し、同名の別店舗の価格を流用しない。

## 2. 料金の事実と概算を分離する

少なくとも以下を表現できる契約にする。

- 料金種別：入場料／企画展／飲食メニュー／価格帯など
- 金額・通貨・下限／上限（欠測は null）
- 上限を含むかどうか
- 単位：一人／一品／セット／グループ／不明
- 対象：一般・子ども等
- 利用種別：常設展／企画展／入園／飲食など
- 適用日・曜日・時間帯・除外条件
- 税・追加料金の扱い（不明なら不明）
- 出典 URL・根拠の引用・取得日時・再確認期限
- 確認状態

「公式単価を確認済み」と「二人の会計が確定」を同じ状態にしない。

## 3. 施設と飲食で計算方法を分ける

### 施設

- 適用条件が合う公式単価から、人数に応じてコードで計算する。
- 一般 2 人を既定にするなら、その仮定を表示する。
- MOT の常設料金を企画展料金として使わない。
- 無料日は対象日・条件が確認できた場合だけ適用する。
- 利用種別が不明なら、明示した仮定で概算するか未確認にする。

### 飲食

- 実メニューの単価を根拠に、注文の仮定を置いた概算を作れるようにする。
- 例：二人が各 1 ドリンク＋各 1 スイーツ。
- 訪問目的と時間帯に合う注文を使う。
- 平日限定セットを土日祝に適用しない。
- 注文の仮定、計算内訳、出典を保持する。
- 「二人の目安」と表示し、確定額や保証された上限と呼ばない。
- 根拠がない金額をモデルの知識だけで埋めない。

## 4. 既存の料金処理を修正する

- Places priceRange を無条件で costForTwoJpy に入れない。
- 単位不明の価格帯は、二人分とは別に保持する。
- startPrice のみの場合、min=max にせず上限不明とする。
- endPrice の境界を維持する。
- priceLevel を根拠なく円額へ変換しない。
- 欠測を 0 円・無料にしない。
- 既存の人数未確認データを、移行時に確認済みへ格上げしない。

## 5. プラン生成へ接続する

プラン生成時は、収集済み料金情報を読み、コードで計算する。追加の LLM 呼び出しは不要とする。

- 日付・人数・利用種別・訪問時間への適用可否を確認する。
- 確認済み条件付き料金／概算／未確認を区別する。
- 概算がある場合は「概算で予算内」と表現できるが、「上限保証」「必ず予算内」とはしない。
- 一部不明なら、判明分の小計と未確認項目を示す。
- 判明分だけで予算超過している場合は、不明項目があっても見逃さない。
- 交通費が欠けている場合、総額に含まれていないことを明示する。
- 古い保存済みプランや確定済み行程を、収集完了だけで勝手に変更しない。

## 6. 非同期実行・保存

既存の日次収集と Worker を再利用する。

- 料金不足を検知した施設を、バックグラウンドの調査対象にできるようにする。
- 同じ施設への重複ジョブを抑止する。
- 費用・検索回数・取得ページ数・実行時間に上限を設ける。
- 取得失敗で既存の根拠付きデータを無条件に消さない。
- 期限切れ情報を黙って最新として扱わない。
- 料金レコード・証拠・実行ログを、増え続ける単一文書に集約しない。
- モデル、使用量、費用、調査理由、取得結果、停止理由を記録する。
- 収集費用を、参照した全プランに重複加算しない。

## 7. 表示

現在のレイアウトを維持し、施設ごとに以下を表示できるようにする。

- 条件付き計算：「一般 2 名・常設展」
- 概算：「二人の目安／各 1 ドリンク＋スイーツを想定」
- 未確認：「料金情報を確認できませんでした」
- 出典リンク・確認日

価格情報を取得できても、適用条件が不明ならその理由を示す。単に COST_UNKNOWN を非表示にする対応は禁止。

## 8. 検証

まず以下の 3 施設で、実検索・実取得・保存・プラン参照を確認する。

- 東京都現代美術館（MOT）
- 清澄庭園
- ヒキダシ

料金額は以前の調査報告を固定値として使わず、今回取得した根拠で確認する。

追加の回帰テスト：

- 一人料金から二人分を計算できる。
- 単位不明の Places 価格帯を二人料金にしない。
- 下限のみの金額を予算上限として使わない。
- 平日限定・無料日・企画展別料金を取り違えない。
- 飲食概算の注文仮定と計算内訳が一致する。
- 公式単価が VERIFIED でも会計概算は ESTIMATED のまま（注文仮定がある場合）。
- 取得失敗・期限切れ・別支店・根拠不一致を安全に扱う。
- 同一施設の重複実行でレコードが増殖しない。
- 通常のプラン生成に LLM 待ちが追加されない。

## 完了報告に含めること

- 実装した構成と対象コミット
- 3 施設の補完前後の料金状態・根拠・適用条件
- 実行 ID・モデル・所要時間・費用
- 単体／実 API／画面確認を区別した結果
- 未実施・残っている制約

実キーがない場合も、実装と可能な検証は完了させ、実接続の未実施を明記する。

本番移行、マージ、デプロイ、Scheduler 有効化は行わない。
